# Ninja

Ninja is a small, fast build system focused on speed. Unlike Make, Ninja build files are not meant to be written by hand — they are generated by higher-level tools like **CMake** ([ch22](22_cmake.md)) or **Meson** ([ch26](26_meson.md)). Ninja's only job is to execute the build as fast as possible.

Ninja was developed by Evan Martin at Google in 2012 to speed up the Chromium build, which was too large for Make to handle efficiently. Notable projects that use Ninja include:

- **Chromium** — open-source browser engine (via GN build generator)
- **Android** — mobile OS build system (via Soong)
- **CMake** and **Meson** projects — Ninja is the default backend for both

The typical workflow has two layers — a generator creates the `build.ninja` file, then Ninja executes it:

```
Developer writes:       Generator produces:       Ninja executes:
─────────────────       ───────────────────       ────────────────
CMakeLists.txt    →     build.ninja           →   compile, link
meson.build       →     build.ninja           →   compile, link
BUILD.gn          →     build.ninja           →   compile, link
```

## Ninja vs Make

| Aspect              | Make                                 | Ninja                                  |
| ------------------- | ------------------------------------ | -------------------------------------- |
| Build file          | `Makefile` (written by hand)         | `build.ninja` (generated)              |
| Language            | Custom DSL with variables, functions | Minimal — rules and build edges only   |
| Parallelism         | `-j4` (must specify)                 | Automatic (uses all cores by default)  |
| Startup time        | Parses Makefile each run             | Optimized for fast incremental builds  |
| Feature set         | Rich (conditionals, functions)       | Intentionally minimal                  |

Ninja is faster because it does less — no string manipulation, no conditionals, no built-in rules. It trades flexibility for speed.

```
$ sudo apt install ninja-build    # Debian/Ubuntu
$ sudo dnf install ninja-build    # Fedora
$ brew install ninja              # macOS
$ pip install ninja               # via Python (any platform)
```

## Basic Example

A simple project:

```
project/
├── build.ninja
├── main.cpp
├── lib.cpp
└── lib.h
```

```cpp
// lib.h
#ifndef LIB_H
#define LIB_H
void hello_from_lib();
#endif
```

```cpp
// lib.cpp
#include <iostream>
#include "lib.h"

void hello_from_lib()
{
    std::cout << "Hello from lib!" << std::endl;
}
```

```cpp
// main.cpp
#include "lib.h"

int main()
{
    hello_from_lib();
    return 0;
}
```

### The `build.ninja` File

In practice, this file is generated by CMake, Meson, or another tool. We write one here by hand to understand the format:

```ninja
# Variables
cxx = g++
cxxflags = -Wall -O2

# Rules define command templates
rule compile
  command = $cxx $cxxflags -MMD -MF $out.d -c $in -o $out
  depfile = $out.d
  deps = gcc

rule link
  command = $cxx $in -o $out

# Build edges: target: rule inputs
build lib.o: compile lib.cpp
build main.o: compile main.cpp
build myprog: link main.o lib.o

# Default target
default myprog
```

Key syntax:

- **`rule`** — defines a command template. `$in` and `$out` are built-in variables that expand to the input and output files.
- **`build`** — defines a build edge: `build OUTPUT: RULE INPUTS`. This is the equivalent of a Make rule.
- **`default`** — the target(s) built when you run `ninja` with no arguments.
- **`depfile`** and **`deps`** — tells Ninja to read compiler-generated `.d` files for header dependency tracking (equivalent to `-MMD -MP` in [ch09](09_header_file_dependencies.md)).

### Building

```
$ ninja
[1/3] compile lib.cpp
[2/3] compile main.cpp
[3/3] link myprog

$ ./myprog
Hello from lib!
```

Ninja shows a compact progress indicator (`[1/3]`, `[2/3]`, ...) instead of printing each command. To see the full commands:

```
$ ninja -v
```

### Cleaning

```
$ ninja -t clean
```

No need to write a `clean` target — Ninja tracks all generated files and removes them automatically.

## Parallelism

Ninja runs builds in parallel by default, using all available CPU cores:

```
$ ninja          # uses all cores automatically
$ ninja -j4      # limit to 4 jobs (same as make -j4)
$ ninja -j1      # sequential (useful for debugging)
```

This is one of the main advantages over Make, where parallel builds require an explicit `-j` flag.

## Header Dependency Tracking

Ninja supports compiler-generated dependency files via the `depfile` keyword in rules:

```ninja
rule compile
  command = g++ -MMD -MF $out.d -c $in -o $out
  depfile = $out.d
  deps = gcc
```

- **`-MMD -MF $out.d`** — tells the compiler to write header dependencies to a `.d` file.
- **`depfile = $out.d`** — tells Ninja to read that file for dependency information.
- **`deps = gcc`** — specifies the `.d` file format (GCC-style).

After the first build, Ninja knows about header dependencies. If you modify `lib.h`, Ninja rebuilds only the affected object files — just like the Make setup from [ch09](09_header_file_dependencies.md), but configured in the rule rather than in individual compiler flags.

## Using Ninja via CMake or Meson

In practice, you rarely write `build.ninja` by hand. Instead, you use a build system generator:

**CMake:**

```
$ cmake -S . -B build -G Ninja
$ ninja -C build
```

**Meson:**

```
$ meson setup build
$ ninja -C build
```

Both tools generate the `build.ninja` file automatically from their own higher-level build descriptions.
